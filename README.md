# backlog-report

Backlog の課題から **進捗レポート** を作り、Slack と Backlog Wiki に届けるツールです。

- **わかること**: マイルストーンごとの完了率と経過（順調 / やや遅れ / 遅れ）、期限超過・期限間近・開始日を過ぎて未着手の課題、担当者別の負荷
- **グラフ**: ガントチャート（状態で色分け・今日の線）とバーンダウン（理想と実績）
- **届け方**: Markdown ファイル、Slack（Bot トークンなら画像も）、Backlog Wiki のページを上書き
- **動かし方**: その場で確認（report）／ 定期実行（batch）／ Slack ボット（`/progress`）

構成（6 層）と動かし方の違いは [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) を参照してください。

## すぐ使う（モックで試す）

API キーが無くても、同梱の架空のデータ（`samples/backlog/`）で試せます。

1. clone する
2. **Windows**: `setup.cmd` をダブルクリック ／ **macOS・Linux**: `./setup.sh`
3. 実行する

```bash
backlog-report -c samples/config.yaml report                       # 画面に Markdown
backlog-report -c samples/config.yaml report --milestone "フェーズ2 製造"
backlog-report -c samples/config.yaml batch --wiki                 # output/ にレポートとグラフ、Wiki はモックのフォルダへ
```

## 本番の Backlog で使う

1. `config.yaml`（setup がコピー済み）の `backlog.space_url` と `project_key` を自分のプロジェクトに直す
2. `.env` に `BACKLOG_API_KEY` を書く（Backlog の 個人設定 → API で発行。**.env はコミットしない**）
3. `backlog-report report` で確認する

| 設定（config.yaml） | 意味 |
|---|---|
| `report.done_statuses` | 完了とみなす状態（既定: 完了。処理済みも含めるなら `[処理済み, 完了]`。1 つだけなら `完了` と書いてもよい） |
| `report.milestones` | 対象のマイルストーン（空ならアーカイブ以外のすべて） |
| `report.due_soon_days` | 何日以内を「期限間近」とするか（既定 3） |
| `report.timezone` | 「今日」と課題の更新日時の日付を決めるタイムゾーン（既定 `Asia/Tokyo`。環境変数 `BACKLOG_REPORT_TIMEZONE` が優先） |
| `report.parent_child` | 完了率・バーンダウン・担当者別の残り時間で、親課題・子課題をどう数えるか（下の表。既定 `children`） |
| `slack.channel` | Bot トークンで投稿するチャンネル ID |
| `wiki.page` | 上書きする Wiki のページ名（手で編集しても次回の実行で上書きされる） |

API キー・トークンを config.yaml に書くとエラーで止まります（誤ってコミットしないため）。

親課題と子課題を両方数えると、同じ作業を二重に数えて完了率・残り時間がずれます。`report.parent_child` で数え方を選べます。

| `parent_child` | 数える課題 | 例: 親 1 件＋子 3 件（子 2 件が完了） |
|---|---|---|
| `children`（既定） | 子課題がある親課題は数えず、子課題で数える | 3 件中 2 件（67%） |
| `parents` | 親課題がある子課題は数えず、親課題で数える | 1 件中 0 件（0%） |
| `both` | すべて数える（以前の動き） | 4 件中 2 件（50%） |

対象（マイルストーン・担当者で絞った結果）の中に子課題がない親課題や、親課題がない子課題は、どの設定でも 1 件として数えます。
マイルストーンごとの完了率・バーンダウン・毎日の記録は、**そのマイルストーンの課題の中だけ** で二重計上を避けます。
親と子が別のマイルストーンにあるとき（親は M1、子は M2）は、親は M1 で、子は M2 で数えます（全体の完了率は対象全体で二重計上を避けます）。
バーンダウンの単位（件数／見積時間）も、実際に数える課題（子のある親を除いた課題など）に見積時間があるかで決めます。
この設定は次の 3 つに同じように効きます。

- 完了率（全体・マイルストーンごと）の件数と見積時間
- バーンダウン（理想線の総量・実績・毎日の記録 `data/snapshots.csv`）
- 担当者別の残り時間（例: 親 12h・子 4h×2 のとき、`children` なら子の 8h だけ。親の 12h を足して 20h にはしない）

期限超過・期限間近の一覧と、担当者別の件数（未完了・期限超過）は、この設定に関係なくすべての課題で数えます（親課題にも期限や担当者があるため）。
設定を途中で変えると、それまでの記録と数え方が変わるので、バーンダウンの線がその日で段になります。

リストの設定項目（`report.done_statuses`・`report.milestones`）は、値が 1 つなら文字列で書いても 1 要素のリストとして読みます。
リストでも文字列でもない値（`{...}` やリストの入れ子）は設定の誤り（終了コード `2`）にします。

## Slack

| 方法 | .env | できること |
|---|---|---|
| Incoming Webhook | `SLACK_WEBHOOK_URL` | 文章の投稿のみ |
| Bot トークン | `SLACK_BOT_TOKEN`（chat:write, files:write） | 投稿とグラフの画像 |
| ボット（Socket Mode） | 上に加え `SLACK_APP_TOKEN`（connections:write）と、スラッシュコマンド `/progress` の登録 | `/progress`、`/progress マイルストーン名`、`/progress @担当者名`、`/progress … --channel` |

`/progress` の応答は、**既定では打った本人にだけ見えます**（ephemeral）。期限超過の課題名や担当者名をチャンネル全員に出さないためです。
チャンネルのみんなに見せるときだけ `--channel` を付けます（例: `/progress "フェーズ2 製造" --channel`）。知らないオプション（`--chanel` など）は
本人だけに見えるエラーで返します。

Slack アプリの作成とトークンの発行は、Slack のワークスペースの管理者のルールに従ってください（無料プランでも使えます）。

Slack の上限（1 つの section は 3000 字、1 メッセージは 50 ブロック）を超えると投稿そのものが拒まれるため、
マイルストーンと期限超過の一覧は上限に収まるだけ載せ、残りは「…ほか N 件」とまとめます（全件はレポートの Markdown・Wiki にあります）。

## 定期実行

`docs/examples/scheduled-report.yml` が GitHub Actions の例です。毎朝実行して残量を記録し、Slack と Wiki へは月曜の朝（と手動実行のとき）だけ送ります。
Windows のタスクスケジューラなら `backlog-report batch --slack --wiki` を登録します。

- 「今日」は PC やサーバーの時計ではなく、`report.timezone`（既定は日本時間）で決めます。GitHub Actions は UTC で動くので、
  UTC 23:50（日本時間 8:50）に実行しても、レポートの日付・期限超過の判定・記録の日付は日本時間の日付になります
- 例では、記録（`report` ジョブ）と通知（`notify` ジョブ）を分けています。Slack や Wiki への送信が失敗しても、
  その日の記録は `save-snapshots` ジョブで `report-data` ブランチに残ります
- 例の actions はコミット SHA で固定し、依存は `constraints.txt` で版を固定して入れます

バーンダウンの実績は `batch` を実行するたびに `data/snapshots.csv` に 1 日 1 行ずつ記録されるので、毎日実行すると正確になります。
この記録は**消えると取り戻せない**ので、置き場所に気をつけてください。

- **GitHub Actions**: 例では、記録を専用のブランチ `report-data` にコミットして残します（無料・期限なし）。
  Actions のキャッシュは 7 日使わないと消えるので使いません。リポジトリへの書き込み権限（`contents: write`）は記録をコミットするジョブだけに与え、
  Backlog・Slack の秘密情報を使うジョブは読み取りだけです。初回は `report-data` ブランチが無くても自動で作ります。
  ブランチが「無い」のか「読めない」（通信の失敗・権限）のかは `git ls-remote --exit-code` で区別し、読めないときは
  空の記録で上書きしないようジョブを止めます
  `report-data` は記録だけのブランチなので、main にマージしないでください。過去の記録は `git log report-data` で追えます
- **自分の PC やサーバー**: `data/` をバックアップの対象にしてください

記録のファイルは一時ファイルに書いてから置き換えるので、書き込みの途中で止まっても、それまでの記録は消えません。

記録の日付は `2026-10-01` のほか、Excel で開いて保存したときの `2026/10/01`（`2026/10/1` も可）も読みます。
日付や残量が読めない行があっても止めずに、その行だけ飛ばして「`警告: 残量の記録 snapshots.csv の 5 行目を飛ばしました（…）`」と
ファイル名・行番号を出します（記録は続けます。飛ばした行はファイルから消さないので、直せば次の実行から使われます）。

`batch` の `--today` に今日（`report.timezone` での日付）より前の日付を指定すると、レポートは作りますが、残量の記録と
Slack に送った記録（`slack.post_log`）は付けません。その日の記録を今の課題の状態で上書きしないためです（警告を出します）。
`report.today`（設定ファイル）は試行・テスト用の固定日付で、この扱いの対象外です。

記録がない日がある（実行が止まっていた・記録ファイルが消えた）と、`batch` は次のような警告を出します。その日の実績は課題の最終更新日からの推定になるので、
線が実際とずれることがあります。

```text
警告: バーンダウン フェーズ2 製造: 記録がない日が 2 日（2026-09-29〜2026-09-30）。その日の実績は課題の最終更新日からの推定です（…）
```

マイルストーンの途中で使い始めたときも、それより前の日は記録がないので同じ警告が出ます。

## 終了コード

| コード | 意味 | 例 |
|---|---|---|
| `0` | 正常 | |
| `1` | 期限超過あり（`--fail-on-delay` のとき） | |
| `2` | 設定・引数の誤り | API キーが無い・設定ファイルの誤り・Backlog が `401`（API キーが無効）／`403`（権限が無い）／`404`（プロジェクトキー・`space_url` の誤り）を返した |
| `3` | 実行時エラー | Backlog の 429・5xx・通信の失敗（再試行しても駄目なとき）・JSON でない応答、Slack の失敗 |

Backlog からの読み取り（GET）は、混雑（429）やサーバーの一時的なエラー（5xx）・通信エラーのとき、少し待って最大 3 回まで再試行します。
Wiki の更新（POST / PATCH）と Slack への投稿は、二重に登録・投稿しないよう再試行しません（失敗したら終了コード `3`）。
Backlog が 200 でも JSON でない本文（プロキシのログイン画面やメンテナンスの HTML など）や、期待した形でない応答を返したときは、
設定の誤りではなく実行時エラー（終了コード `3`）として、応答の種類と先頭を表示して止めます。Wiki の更新でこうなったときは、
更新が届いている可能性があるので Wiki を確かめてください。
Slack ボット（`/progress`）は、引用符が閉じていない入力や Backlog の読み取りの失敗（JSON でない応答を含む）も、本人にだけ見えるメッセージで返します。

Slack に送った本文と画像は `slack.post_log`（既定 `data/posted.csv`）に 1 件ずつ記録し、同じ日・同じ送り先・同じプロジェクトには
二度送りません（再実行や、画像の途中で失敗したあとの再実行で同じレポートが 2 回投稿されないように）。送り直すときは `batch --slack --force-post`。
定期実行の例では、この記録も `snapshots.csv` と一緒に `report-data` ブランチに保存します。

Slack に送る文章の `&` `<` `>` は、課題の件名などに含まれていても書式やメンションにならないようエスケープします。
Markdown・Wiki の表では、件名・マイルストーン名・担当者名・状態名の `|` を「／」に、改行を空白にして、列がずれないようにします。

## 開発

```bash
./setup.sh                    # Windows: setup.cmd
pip install -e ".[dev,bot]" -c constraints.txt   # 依存の版を CI と同じにする（constraints.txt は GitHub Actions の deps-lock が作る）
ruff check . && ruff format --check . && pytest
```

CI は Linux と Windows でテストを流し、bandit（SAST）と pip-audit（依存の脆弱性）も行います。

テストはモックと偽の HTTP で動き、Backlog・Slack には接続しません。

## 変更点

### 2026-10（fix/score-up-2）

- `report.first_status`（既定 `未対応`）で「未着手」とみなす状態名を変えられます（状態名を変えたプロジェクト向け）
- ガントチャートは、開始日の順に並べてから先頭 40 件を描きます（以前は先に 40 件で切っていたため、早い課題が抜けることがありました）
- Slack への二重投稿を防ぐ記録 `data/posted.csv` と `batch --force-post` を足しました。
  定期実行の例をコピーして使っている場合は差し替えてください（report-data の取得の失敗で記録を消さないようにもなりました）

### 2026-10（fix/score-up-1007）

利用者の動きが変わるもの:

- 「今日」を OS の日付ではなく `report.timezone`（既定 `Asia/Tokyo`）で決めます。UTC で動く環境では、
  レポートのファイル名・期限超過の判定・`data/snapshots.csv` の日付が、以前より 1 日後ろ（日本時間の日付）になります
- 課題の作成日時・更新日時も、UTC ではなく同じタイムゾーンの日付にします（バーンダウンの推定に使う完了日が変わることがあります）
- 定期実行の例（`docs/examples/scheduled-report.yml`）を、記録・保存・通知の 3 つのジョブに分けました。
  コピーして使っている場合は差し替えてください（`constraints.txt` を使うので、リポジトリにそのファイルが必要です）
